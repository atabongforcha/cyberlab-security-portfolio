# Failed Logon Detection

## Project Overview

This project demonstrates the detection and validation of failed Windows authentication attempts using Splunk Enterprise and Windows Security Event ID `4625`.

Windows security events generated by the Active Directory domain controller `DC01` were ingested into Splunk. A security-focused SPL search was used to identify failed logons, extract the affected account name, and count failed attempts. The detection was validated against events in the `WinEventLog:Security` sourcetype.

## Detection Architecture

The detection workflow consisted of:

1. A failed authentication attempt occurred within the Windows domain environment.
2. Windows recorded the activity as Security Event ID `4625`.
3. The Windows security event was collected and ingested into Splunk.
4. Splunk stored the event under `WinEventLog:Security`.
5. An SPL search filtered the events by host and Event ID.
6. The search extracted `TargetUserName`.
7. Failed attempts were counted by account.
8. The search results were reviewed and validated against the original Windows event.

## About Event ID 4625

Windows Security Event ID `4625` is generated when an account fails to log on.

This event can help detect or investigate:

* Incorrect passwords
* Repeated authentication failures
* Brute-force attempts
* Password-spray activity
* Attempts involving disabled or restricted accounts
* Service-account authentication failures
* Scheduled tasks using outdated credentials
* Misconfigured applications or services
* Unauthorized access attempts

A single Event ID `4625` does not automatically prove malicious activity. The event must be analyzed using the account, host, timestamp, logon type, failure reason, source information, and surrounding authentication activity.

## Relevant Event Fields

The following fields are useful when investigating Event ID `4625`:

| Field              | Investigative Value                                |
| ------------------ | -------------------------------------------------- |
| `TargetUserName`   | Identifies the account that failed to authenticate |
| `TargetDomainName` | Identifies the associated domain                   |
| `ComputerName`     | Identifies the system that recorded the event      |
| `LogonType`        | Indicates the type of authentication attempt       |
| `Status`           | Provides the authentication failure status         |
| `SubStatus`        | Provides additional failure detail                 |
| `FailureReason`    | Describes why authentication failed                |
| `IpAddress`        | May identify the source address when available     |
| `WorkstationName`  | May identify the originating workstation           |
| `_time`            | Establishes when the activity occurred             |
| `host`             | Identifies the Splunk source host                  |
| `sourcetype`       | Identifies the ingested event format               |

Not every field is populated in every Event ID `4625` record. Available fields depend on the logon type, authentication method, system configuration, and source of the attempt.

## Detection Logic

The detection follows this analytical pattern:

* **Data source:** Windows Security events
* **Host scope:** `DC01`
* **Event filter:** Event ID `4625`
* **Account field:** `TargetUserName`
* **Aggregation:** Count failed attempts by account
* **Time scope:** Analyst-selected investigation window
* **Output:** Account name and number of failed attempts

## Security Analysis

### Indicators That May Increase Suspicion

* Many failures involving one account
* Failures involving multiple accounts from one source
* Attempts occurring within a short period
* Failures involving privileged accounts
* Attempts outside expected working hours
* Repeated activity from an unfamiliar workstation or address
* Failed logons followed by a successful logon
* Lockout activity following repeated failures

### Potential Benign Causes

* A user entering an incorrect password
* An expired password
* Cached credentials
* A service using an outdated password
* A scheduled task with invalid credentials
* A disconnected mapped drive
* A misconfigured application
* Normal user error

### Analyst Response

When suspicious patterns are identified, an analyst should:

* Review the affected account
* Determine whether the account is privileged
* Review the source system and address
* Examine the failure reason and logon type
* Search for related authentication events
* Look for a successful logon after the failures
* Review account-lockout activity
* Contact the account owner when appropriate
* Reset credentials or contain the account if compromise is confirmed
* Document the investigation and outcome

## Challenges and Resolutions

### Event Not Appearing in Splunk

**Challenge:** A failed-logon event may not appear if the wrong time range, host, source, or Event ID is selected.

**Resolution:** Confirmed the source event in Windows Event Viewer, selected the correct time range, and filtered the Splunk data by host and Event ID.

### Field Extraction

**Challenge:** Raw Windows events can be difficult to summarize when the relevant account field is not displayed clearly.

**Resolution:** Extracted `TargetUserName` and aggregated the results by account to create an analyst-readable result.

### Distinguishing Malicious and Benign Activity

**Challenge:** A failed logon can result from user error or an operational issue rather than an attack.

**Resolution:** Evaluated the number of attempts, account type, time, source, failure reason, and surrounding authentication events before assigning security significance.

### Limited Context from One Event

**Challenge:** A single Event ID `4625` does not provide the complete context of an authentication incident.

**Resolution:** Used the event as an initial detection signal and reviewed related authentication, lockout, account, and source activity.

## Lessons Learned

* Event ID `4625` is a foundational Windows authentication-detection source.
* Reliable detection depends on correct audit configuration and log ingestion.
* Windows Event Viewer should be used to validate the original event.
* Search time ranges strongly affect investigation results.
* Extracting and aggregating account fields makes raw events easier to analyze.
* A single failed logon does not necessarily indicate malicious activity.
* Detection thresholds and contextual fields help separate user error from suspicious behavior.
* Failed-logon monitoring provides the foundation for brute-force and password-spray detection.
* Privileged-account failures should receive additional scrutiny.
* Detection logic should be tested with known events before operational use.
* Sanitized screenshots strengthen the credibility of portfolio documentation.
